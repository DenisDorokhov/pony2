Offline H2 discovery result migration for Codex

Purpose

Migrate an existing local Pony2 database to SQL NULL task results and Spotify
artist results without a status field. This is a one-time data migration, not a
schema migration. Do not add a Flyway migration or modify tables or indexes.
Do not start the Spring application to perform this migration.
Use docs/MigrateDiscoveryResults.java, the standalone Java 21 source runner
included alongside these instructions. Its database base path is a required
argument; no developer-specific database path is compiled into it.

1. Locate and stop the application

Read the actual launch configuration, environment variables and property
overrides. The defaults in backend/src/main/resources/application.properties are:

  pony.home=${user.home}/.pony2
  spring.datasource.url=jdbc:h2:${pony.home}/db/pony;DB_CLOSE_ON_EXIT=FALSE;CACHE_SIZE=262144
  spring.datasource.username=sa
  spring.datasource.password=

Do not assume the default path or credentials if the launch configuration
overrides them. Resolve the absolute database base path and verify that its
existing .mv.db file exists. The JDBC path must omit the .mv.db extension.
Always supply this base path explicitly on the machine being migrated. The
developer's ~/.pony2 location is not a server configuration or a fixed path in
the runner. Server installations may store the database anywhere.
Confirm that the application and other database clients are stopped. If H2
reports a database lock, stop and resolve the open connection; never remove lock
files or force access to an open database.

2. Back up the closed database

Copy the existing .mv.db file to a timestamped backup outside the database
directory. Record the original and backup paths, size and SHA-256 hash; confirm
that the copy matches. Keep the backup until the updated application is verified.
Make a separate working copy in a temporary directory for the rehearsal. Never
rehearse against the original database or the only backup.

Use native PowerShell file operations with -LiteralPath. For example, after
setting $migrationDbBase to the verified absolute base path:

  $migrationDbFile = Get-Item -LiteralPath ($migrationDbBase + '.mv.db')
  $migrationStamp = Get-Date -Format 'yyyyMMdd-HHmmss'
  $migrationBackupRoot = Join-Path ([Environment]::GetFolderPath('UserProfile')) '.pony2-backups'
  $migrationWork = Join-Path $migrationBackupRoot ('pony2-result-migration-' + $migrationStamp)
  New-Item -ItemType Directory -Path $migrationWork
  $migrationBackup = Join-Path $migrationWork 'pony-backup.mv.db'
  $migrationCopy = Join-Path $migrationWork 'pony-rehearsal.mv.db'
  Copy-Item -LiteralPath $migrationDbFile.FullName -Destination $migrationBackup
  Copy-Item -LiteralPath $migrationBackup -Destination $migrationCopy
  Get-FileHash -Algorithm SHA256 -LiteralPath $migrationDbFile.FullName
  Get-FileHash -Algorithm SHA256 -LiteralPath $migrationBackup

3. Prepare an isolated JDBC runner

Use the H2 version resolved by the updated application, not an arbitrary H2
download. Use the application's Jackson JSON parser. Resolve the runtime
classpath without starting the application. From the repository root, write this
temporary Gradle init script to $migrationWork/classpath.gradle:

  gradle.projectsEvaluated {
      def backendProject = gradle.rootProject.project(':backend')
      backendProject.tasks.register('printH2MigrationClasspath') {
          doLast {
              println backendProject.configurations.runtimeClasspath.asPath
          }
      }
  }

Normalize the init script to UTF-8 without BOM, then resolve the classpath:

  $migrationInit = Join-Path $migrationWork 'classpath.gradle'
  $migrationInitSource = [System.IO.File]::ReadAllText($migrationInit)
  [System.IO.File]::WriteAllText($migrationInit, $migrationInitSource, [System.Text.UTF8Encoding]::new($false))
  $migrationClasspath = (& .\gradlew.bat -q -I $migrationInit :backend:printH2MigrationClasspath --console=plain | Select-Object -Last 1)
  if ($LASTEXITCODE -ne 0) { throw 'Could not resolve the migration classpath.' }

The full runtime classpath can exceed the Windows command-line length limit.
Pass it through a UTF-8 Java argument file, using forward slashes so Java does
not interpret Windows path separators as escape sequences:

  $migrationJavaArgs = Join-Path $migrationWork 'java.args'
  $migrationJavaArgsContent = @('--class-path', ('"' + $migrationClasspath.Replace('\', '/') + '"'))
  [System.IO.File]::WriteAllLines($migrationJavaArgs, $migrationJavaArgsContent, [System.Text.UTF8Encoding]::new($false))

Copy the provided runner into the migration work directory and keep that exact
version for rehearsal and live execution:

  $migrationRunner = Join-Path $migrationWork 'MigrateDiscoveryResults.java'
  Copy-Item -LiteralPath 'docs/MigrateDiscoveryResults.java' -Destination $migrationRunner
  & java ('@' + $migrationJavaArgs) $migrationRunner --self-test
  if ($LASTEXITCODE -ne 0) { throw 'Migration self-test failed.' }

The runner uses JDBC and JSON trees, preserves nested fields and reports counts
without logging complete results or credentials. It accepts an absolute database
base path without the .mv.db extension, constructs a local JDBC URL with
IFEXISTS=TRUE, and opens --dry-run and --verify databases read-only. It defaults
to user sa and an empty password. Override PONY_MIGRATION_USER and
PONY_MIGRATION_PASSWORD in the process environment if the installation uses
different credentials. Do not put passwords into saved commands or reports.

These PowerShell examples are for Windows. On a Unix server use ./gradlew
instead of .\gradlew.bat and prepare the Java argument file with that server's
resolved runtime classpath. The same Java source and modes work on either OS;
always pass the server's actual absolute database base path. For example:

  java @/path/to/java.args docs/MigrateDiscoveryResults.java /actual/pony-home/db/pony --dry-run

4. Transformation rules

Inspect discovery_task.id, type, status and result. Preserve every column except
result, including task status, creation_date, update_date, associations and raw
request/response data. The only other permitted data change is clearing
artist_discovery_index.spotify_artist_id under rule D below. Preserve the other
columns of that table, including its dates, and preserve all other tables,
including discovery_cache and flyway_schema_history.

Apply these rules in order:

  A. For every task type and lifecycle status, replace result containing exactly
     the four-character JSON token null with SQL NULL. Bind it with
     PreparedStatement.setNull(..., Types.VARCHAR), never the text "null".
     A JSON string value whose contents are null is not this JSON null token.

  B. For SPOTIFY_ARTIST_DATA JSON objects with a root status of NOT_FOUND or
     AMBIGUOUS, replace the entire result with SQL NULL.

  C. For SPOTIFY_ARTIST_DATA JSON objects with a root status of FOUND, remove
     only that root property and serialize the remaining object. Preserve all
     other JSON values, including nulls, empty arrays and unknown properties.
     Verify artist and matchedAlbum are non-null objects before accepting FOUND.

  D. After transforming task results, inspect the latest COMPLETE
     SPOTIFY_ARTIST_DATA task for each existing artist, using creation_date DESC,
     id DESC (not update_date or job status). If that task's transformed result
     is SQL NULL, clear spotify_artist_id in the existing artist_discovery_index
     row. Include results that were already SQL NULL. Do not create index rows,
     change MusicBrainz IDs/country/dates, or clear an ID because of an older
     empty task when a newer completed task has data. If the latest completed
     result has data, or no completed task exists, leave the index unchanged.
     Failed, interrupted and started tasks do not supersede a completed task.

Already SQL NULL results are unchanged. Already migrated Spotify results without
a root status are unchanged, provided completed task data has valid artist and
matchedAlbum objects. Leave error objects for unsuccessful tasks unchanged.
Non-Spotify results other than rule A are unchanged. Report malformed JSON,
unknown root statuses or unexpected completed Spotify data with task IDs and
abort before changing anything; do not guess or silently discard such rows.

Use direct JDBC updates so application entity auditing does not change dates.
Use one transaction with autoCommit=false, and commit only after all changes and
checks succeed. On any exception, roll back the whole transaction. Do not split
the migration into independently committed batches. For --dry-run, do not write.

5. Rehearse and verify

Pass the working copy's base path, not the backup or original. For example:

  $migrationCopyBase = Join-Path $migrationWork 'pony-rehearsal'
  $migrationBackupBase = Join-Path $migrationWork 'pony-backup'
  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationCopyBase --dry-run
  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationCopyBase --apply
  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationCopyBase --dry-run
  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationCopyBase --verify $migrationBackupBase

Check each command's exit code before continuing. Verify that the second dry run
proposes zero changes. Test the runner on synthetic records as well: JSON null
for each task type, SQL NULL, FOUND with optional nulls and nested status fields,
both negative statuses, empty arrays, arrays containing null, unsuccessful error
results, already migrated data, and malformed data causing a full rollback.
Also cover an old empty result followed by FOUND, a newer empty result after
FOUND, creation-date ties resolved by ID, a newer failed task, an already SQL
NULL latest result, a missing index row, and preservation of MusicBrainz/country
fields and dates. The repeated dry run must propose zero index changes too.

Before committing --apply, compare the proposed JSON transformations with the
original trees and verify that unaffected result values, all other columns,
row counts, schema definitions and other table contents are unchanged, except
for the explicitly planned spotify_artist_id clears in rule D. Report that
count separately and verify that every cleared ID satisfies rule D. The runner
compares SHA-256 digests of every row of every PUBLIC table, including duplicate
rows, with only the explicitly planned cell changes substituted. It also checks
the schema script, repeats preflight for idempotence before commit and checks
again after reconnecting. --verify independently compares the migrated database
against the expected transformation of the read-only backup. The SQL
NULL count must increase by exactly the counts from A and B; changes from C
must equal the number of FOUND objects. After committing, reconnect and repeat
the read checks. Useful SQL checks include:

  SELECT COUNT(*) FROM discovery_task WHERE result = 'null';
  SELECT type, status, COUNT(*) FROM discovery_task WHERE result IS NULL GROUP BY type, status;
  SELECT COUNT(*) FROM discovery_task WHERE status = 'COMPLETE' AND result IS NULL;

The first query must return zero. Also parse every non-null completed Spotify
result to confirm that it has no root status and has valid artist/matchedAlbum.
Historical rawResult and cached LLM responses retain their original statuses.

6. Apply to the original database and recover if necessary

Keep the application stopped. Confirm the original database still matches the
backup hash; if it changed, investigate and repeat backup/preflight. Use the
verified original base path. Repeat --dry-run, --apply and --verify against the
original, checking each exit code before the next command:

  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationDbBase --dry-run
  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationDbBase --apply
  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationDbBase --dry-run
  & java ('@' + $migrationJavaArgs) $migrationRunner $migrationDbBase --verify $migrationBackupBase

Retain a copy of the count reports and backup metadata. Do not run unverified runner changes
against the original after the rehearsal. Close every JDBC connection before
starting the updated application. Check task details, No Result filtering and
artist/top-track discovery. Retain the backup and the count report.

For a failure before commit, roll back and close the connection. For a failure
after commit, keep or stop the application, close all database clients, preserve
the failed migrated file separately and restore the verified backup to the exact
original .mv.db path. Verify its hash before use. A restored old-format database
requires the previous application version or a corrected offline migration
before the updated application can be started.
