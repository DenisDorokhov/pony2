Инструкция для Codex: серверная миграция raw_requests / raw_results

Задача

Приведи существующую серверную H2-базу Pony2 к текущему коду:

  - discovery_task.raw_request -> raw_requests;
  - discovery_task.raw_result -> raw_results;
  - строковые элементы массива raw_results -> значения по точным правилам
    JsonConverter.fromJsonOrString из целевого приложения.

Имена колонок уже изменены в backend/src/main/resources/db/migration/V2__discovery.sql.
Схему существующей БД обнови вручную и синхронизируй только checksum V2 после
проверки соответствия схемы. Новую Flyway-миграцию и изменения кода приложения
для этой операции не добавляй.

Это отдельная операция от docs/H2_RESULT_MIGRATION.txt и
docs/MigrateDiscoveryResults.java. Тот runner меняет колонку result и Spotify
индексы, поэтому для данной задачи его не запускай.

Содержимое result, raw_requests, статусы, даты, связи задач, discovery_cache,
artist_discovery_index и остальные данные приложения должны сохраниться.
Допустимы только два переименования колонок, адресное обновление checksum V2
и описанное ниже изменение содержимого raw_results.

На сервере данных существенно больше, чем в локальной базе. Используй
ограниченную память, короткие транзакции и проверяемое возобновление обработки.
Не переноси в серверную процедуру локальные пути, количество строк и checksum.

1. Установи фактическую конфигурацию

Найди способ запуска приложения: systemd, Docker Compose, другой менеджер
процессов. Прочитай реальные аргументы запуска, environment, pony.properties,
Spring properties и привязки томов контейнера. Определи:

  - абсолютный путь существующего файла .mv.db и базовый JDBC-путь без .mv.db;
  - пользователя БД и источник пароля;
  - владельца и права файла, пользователя сервиса;
  - текущую и целевую версии приложения, Java, H2, Jackson и Flyway;
  - расположение V2 из фактически установленной старой версии и целевого V2;
  - команды остановки, запуска и проверки приложения.

По умолчанию application.properties задаёт pony.home=${user.home}/.pony2,
JDBC URL jdbc:h2:${pony.home}/db/pony;DB_CLOSE_ON_EXIT=FALSE;CACHE_SIZE=262144,
пользователя sa и пустой пароль. Это только значения по умолчанию, а не
подтверждение серверной конфигурации. Не создавай новую БД при ошибке в пути:
во всех соединениях указывай IFEXISTS=TRUE и заранее проверяй наличие файла.
Пароли не включай в команды, исходники runner или отчёты; передавай через
защищённое окружение. При дополнительных настройках H2, например шифровании,
сохрани фактические параметры соединения.

Подготовь отдельный каталог операции вне репозитория и зафиксируй целевой
commit/артефакт. Зависимости бери из целевого приложения, не скачивай другую
версию H2. При смене версии H2 между приложениями сначала установи совместимый
способ открытия существующей БД на копии; не обновляй формат оригинала вслепую.
Для standalone Java runner используй Java 21 и tools.jackson из приложения.
Из bootJar можно извлечь BOOT-INF/classes и BOOT-INF/lib и включить в classpath
классы приложения и его библиотеки. При наличии исходников runtimeClasspath
можно получить временной Gradle-задачей без bootRun и старта Spring; дополни
его каталогом скомпилированных классов backend, содержащим JsonConverter
и ListOfObjectsJsonAttributeConverter.

2. Останови приложение и создай проверенную резервную копию

Останови все экземпляры приложения и другие клиенты этой БД. На время операции
исключи автоматический перезапуск сервиса/контейнера, записав прежние настройки.
При блокировке H2 найди открывший файл процесс и корректно закрой его. Не удаляй
lock-файлы и не обходи блокировку работающей БД.

Скопируй закрытый .mv.db в отдельный каталог резервных копий с timestamp.
Запиши исходный и резервный пути, размер, права, владельца и SHA-256; проверь
совпадение хешей. Эту копию больше не изменяй. Для репетиции сделай ещё одну
независимую копию, открываемую на запись. Не используй hard link на оригинал
или единственный бэкап. Для CoW-копии проверь независимость последующих записей.

Оцени свободное место для бэкапа, репетиции, роста H2 и временных файлов runner.
Зафиксируй пиковое потребление диска и памяти при репетиции. Оригинал должен
оставаться закрытым и неизменным до успешного завершения проверки на копии.

3. Подготовь временный runner и режим предварительной проверки

Создай standalone JDBC runner в каталоге операции. Он должен принимать явные
пути рабочей БД и неизменяемого исходного бэкапа и поддерживать dry-run, apply
и verify. Исходный бэкап обязателен во всех трёх режимах. В dry-run и verify открывай
данные только для чтения (ACCESS_MODE_DATA=r). Не запускай Spring для миграции:
обработчики запуска и аудит сущностей могут менять данные и даты.

Сначала собери отчёт на копии: размеры БД, количество задач, SQL NULL в raw
полях, типы корневых JSON-значений и элементов, число потенциальных изменений,
максимальный размер строки, версия/состояние схемы и история Flyway. Не выводи
полные промпты, ответы и секреты; для проблемных строк достаточно id и причины.

До применения проверь runner на синтетической БД:

  - старые, новые и уже частично преобразованные данные;
  - SQL NULL, пустой массив, элементы null;
  - JSON-объект и массив, сохранённые строками, обычный текст и пустая строка;
  - строки с числами, true, false и null, а также закодированные JSON-строки;
  - строку с JSON-строкой "42": результат первого разбора должен остаться
    строкой "42" после повторного запуска, а не превратиться в число 42;
  - невалидный JSON, JSON с хвостом текста и два JSON-документа в одной строке;
  - большие целые и дробные числа, Unicode, переводы строк и кавычки;
  - вложенные текстовые поля с JSON-фрагментами, которые менять нельзя;
  - ошибку записи с rollback текущей порции;
  - остановку после commit до записи checkpoint и успешный повторный запуск;
  - отсутствие изменений при повторной полной обработке.

4. Проверь и при необходимости обнови схему

Используй metadata БД, а не предположения по версии приложения. Для PUBLIC:

  SELECT column_name, data_type
  FROM information_schema.columns
  WHERE table_schema = 'PUBLIC' AND table_name = 'DISCOVERY_TASK';

  SELECT "installed_rank", "version", "script", "checksum", "success"
  FROM "flyway_schema_history" ORDER BY "installed_rank";

Если обе колонки уже имеют новые имена и V2 соответствует целевому файлу,
повторное переименование и обновление checksum не нужны.

Если присутствуют только старые имена, проверь до изменений:

  - V2 успешно применён, его checksum соответствует V2 установленной версии;
  - старый и целевой V2 различаются только этими двумя именами колонок;
  - фактическая схема соответствует ожидаемой старой схеме;
  - другие применённые миграции не имеют необъяснённых расхождений.

При отсутствующем/неуспешном V2, неизвестном checksum, наличии одновременно
старой и новой версии одной колонки или других расхождениях не угадывай схему
и не маскируй проблему repair. Сохрани диагностику и выясни исходное состояние.
Частичное переименование после известного сбоя можно продолжать только по
журналу этой операции и после проверки фактического состояния каждой колонки.

Подтверждённые старые колонки переименуй:

  ALTER TABLE discovery_task ALTER COLUMN raw_request RENAME TO raw_requests;
  ALTER TABLE discovery_task ALTER COLUMN raw_result RENAME TO raw_results;

DDL в H2 коммитится отдельно. Rollback последующей транзакции данных не
отменит переименование. Записывай завершение каждого DDL-шага в журнал.

Вычисли checksum целевого V2 через механизм той версии Flyway, которую
использует целевое приложение. Это не SHA-256 файла и не CRC32 файла вместе
с переводами строк. Не подставляй число с другой машины/версии V2.
После проверки обеих колонок обнови только успешную запись V2 через JDBC:

  UPDATE "flyway_schema_history" SET "checksum" = ?
  WHERE "version" = '2' AND "script" = 'V2__discovery.sql'
    AND "checksum" = ? AND "success" = TRUE;

Первый параметр — проверенный целевой checksum, второй — зафиксированный
исходный. Требуй ровно одну изменённую строку. Другие поля истории сохрани.
Общий Flyway repair не используй: он может скрыть посторонние расхождения.
Вызови Flyway validate для целевых ресурсов через standalone API без старта
приложения и проверь успешный результат. При уже выполненных шагах сверяй
состояние с журналом, а не повторяй UPDATE с произвольным старым checksum.

Сохрани отдельный контрольный снимок схемы и истории Flyway после этого этапа.
Преобразование данных далее не должно менять ни схему, ни историю/checksum.
Закрой соединение фазы DDL; для порций данных используй отдельное соединение
с явно установленным autoCommit=false.

5. Правила преобразования raw_results

Эталон — JsonConverter.fromJsonOrString и ListOfObjectsJsonAttributeConverter
из целевого commit приложения. Используй эти классы из целевого артефакта
или скомпилированных исходников с его runtimeClasspath без запуска Spring.
Если приходится воспроизводить код в standalone runner, проверь совпадение
результатов с этими классами, включая настройки mapper и сериализацию.

Колонка raw_results содержит JSON-массив. Для каждого непосредственного
строкового элемента ИСХОДНОГО массива из бэкапа ровно один раз вызови
JsonConverter.fromJsonOrString. При успешном разборе используй полученное
значение любого JSON-типа: объект, массив, число, boolean, null или строку.

  До:
  ["{\"answer\":42}", "[1,null]", "42", "true", "false", "null", "\"text\"", "\"42\"", "plain text", null]

  После:
  [{"answer":42}, [1,null], 42, true, false, null, "text", "42", "plain text", null]

Таким образом, JSON-строки тоже раскодируются: исходное значение \"text\"
с кавычками становится Java-строкой text. JSON-токен null становится настоящим
null внутри массива. Обычный текст, пустые/пробельные строки, невалидный JSON,
JSON с хвостом текста, несколько документов и Markdown с JSON-фрагментом
сохраняются исходными строками: метод перехватывает JacksonException и
возвращает исходное значение. Другие ошибки не маскируй как обычный текст.

Используй те же правила FAIL_ON_TRAILING_TOKENS и тот же mapper, что в коде.
Не включай отдельно USE_BIG_DECIMAL_FOR_FLOATS, принудительный BigInteger или
обнаружение дубликатов ключей: это изменит поведение относительно приложения.
Текущее округление дробей и выбор последнего значения повторяющегося ключа
приняты как ограничения проекта. Для данной миграции не исправляй их отдельно.
Не используй replace/регулярные выражения, Map.toString() или LlmJsonConverter
с извлечением JSON-фрагментов.

Не разбирай повторно строки, полученные в результате первого вызова, и не
заходи рекурсивно во вложенные поля/массивы разобранного ответа. Уже существующие
нестроковые элементы передавай как есть. SQL NULL и пустые массивы сохраняй.
Количество и порядок элементов не меняются; позиции null могут дополнительно
появиться на месте строк с JSON-токеном null.

Ожидаемое значение вычисляй из бэкапа следующим образом. Для SQL NULL оно
равно SQL NULL. Для непустого или пустого JSON-массива:

  ListOfObjectsJsonAttributeConverter converter = new ListOfObjectsJsonAttributeConverter();
  List<Object> original = converter.convertToEntityAttribute(backupRawResults);
  List<Object> converted = new ArrayList<>(original.size());
  for (Object element : original) {
      converted.add(element instanceof String text ? JsonConverter.fromJsonOrString(text) : element);
  }
  String expected = original.equals(converted)
          ? backupRawResults : converter.convertToDatabaseColumn(converted);

Сериализация должна совпадать с целевым JPA-конвертером; не сравнивай ожидаемые
Java-объекты с результатом повторного чтения вместо сравнения сохранённого JSON.
Например, крайние числовые значения могут сериализоваться иначе, чем выглядят
в памяти. Для задачи без преобразований сохраняй исходный текст побайтно.
Для изменённой задачи ожидаемым является именно результат указанной цепочки
чтения, fromJsonOrString и сериализации, с её текущими числовыми настройками.

Если внешний JSON колонки повреждён или его корень не массив, сообщи id и
останови предварительную проверку. Невалидная строка внутри корректного массива
остаётся ожидаемым raw-ответом. При apply выполняй UPDATE только если текущий
текст raw_results отличается от expected; если уже равен, пропусти запись.
Отдельно считай преобразования относительно бэкапа и необходимые сейчас UPDATE.
После применения первый счётчик может быть ненулевым, но второй должен быть ноль.

Преобразование значений само по себе НЕ идемпотентно: JSON-строка с содержимым
42 после одного разбора становится строкой "42", а её повторный разбор дал бы
число 42. Повторные запуски безопасны только при неизменном источнике — бэкапе
до первого применения. Не используй текущие данные назначения как новый вход
для fromJsonOrString и не создавай новый исходный бэкап из результата миграции.
Если часть ответов уже разбиралась новым кодом или другой миграцией, установи
по исходному бэкапу/журналу, какие записи подлежат преобразованию. По содержимому
строки "42" нельзя определить, старый это ответ или уже разобранная JSON-строка;
при отсутствии доказанного исходного состояния не угадывай и не разбирай её снова.

6. Обработка большого объёма и возобновление

Не собирай все задачи, JSON-деревья или план UPDATE в Map/List в памяти.
Не выполняй одну огромную транзакцию на всю таблицу. JDBC fetchSize сам по себе
не является гарантией ограниченной памяти.

Обходи первичный ключ исходного бэкапа страницами через keyset pagination:

  SELECT id FROM discovery_task WHERE id > ? ORDER BY id LIMIT ?;

Для первой страницы используй запрос без условия id > ?. Не используй OFFSET.
Держи в памяти ограниченную страницу id; JSON каждой задачи загружай из бэкапа,
вычисляй expected по пункту 5 и сверяй с той же задачей в рабочей БД.
Открывай бэкап только для чтения. Допустимы только исходный текст или expected;
при другом текущем значении остановись и выясни причину. Обрабатывай и
освобождай JSON одной задачи за раз. Закрывай ResultSet перед записью/commit.
Пиши через PreparedStatement UPDATE discovery_task SET raw_results = ? WHERE id = ?;
проверяй, что обновлена ровно одна строка. Не используй ORM, чтобы не менять даты.

Начальные ориентиры — страница 200 id и commit после 200 просмотренных задач
или 16 MiB изменённых JSON, в зависимости от того, что наступит раньше.
Подстрой лимиты и Java heap по результатам репетиции; фиксируй настройки в
журнале. Одна большая задача может превысить лимит порции: обработай её
отдельно. Если даже одна строка не помещается в память, используй потоковый
JSON parser/generator и временный файл для этой строки либо заранее увеличь
обоснованный лимит памяти. Не обрезай и не пропускай такие данные молча.

Каждая порция — отдельная транзакция autoCommit=false. При ошибке откатывай
только незакоммиченную порцию; ранее завершённые порции уже сохранены.
После успешного commit атомарно сохраняй checkpoint: последний обработанный
id, номер порции, счётчики, идентификатор БД/бэкапа и хеш runner/целевого V2.
Checkpoint не должен опережать commit. Для dry-run checkpoint apply не меняй.

Сбой между commit и checkpoint может привести к повторной обработке порции.
Для неё снова вычисляй expected из того же бэкапа и пропускай уже совпадающие
записи. Именно это, а не идемпотентность fromJsonOrString, обеспечивает безопасный
повтор. При возобновлении сверяй manifest, хеш бэкапа, runner и фазу схемы.
Если состояние checkpoint не доказано, полный повторный обход с тем же исходным
бэкапом безопаснее пропуска диапазона id. Приложение всё время должно оставаться
остановленным. При необходимости храни построчный план/хеши на диске, не в RAM.

После первых commit хеш рабочего файла БД уже отличается от исходного бэкапа.
При возобновлении это ожидаемо: проверяй строки против бэкапа и разрешённого
преобразования. До checkpoint должны быть ожидаемые преобразованные значения;
после него допустимы исходные значения и уже преобразованная порция, commit
которой опередил checkpoint. Любое другое расхождение требует выяснения причины.

Печатай периодический прогресс: последний id, просмотренные/изменённые задачи,
число преобразований в объекты, массивы, числа, boolean, null и строки,
количество сохранённых исходных строк/null, объём записи, время и скорость.
Значения JSON и пароли в лог не выводи.

7. Полная репетиция и проверка

Выполни на рабочей копии dry-run, фазу схемы при необходимости, apply,
повторный dry-run и verify против неизменённого бэкапа. Проверяй exit code
каждого шага. Во всех режимах используй один исходный бэкап. Повторный dry-run
должен сравнить рабочие данные с expected из бэкапа и предложить ноль изменений,
включая для раскодированных JSON-строк. Разбирать строки рабочей копии заново
для поиска дополнительных преобразований запрещено.

Verify должен читать бэкап и результат независимо, в стабильном порядке id,
с ограниченной памятью. Для каждой задачи вычисли ожидаемый raw_results из
исходного значения бэкапа по пункту 5 и сравни с мигрированной записью.
Учти старые/новые имена колонок при чтении двух схем. Сравни также все остальные
колонки discovery_task: result, raw_requests, статусы, даты и связи — точно
без изменений. Сверь количество задач и порядок/длину массивов. Исходные null
должны сохраниться, новые null допускаются только согласно expected из бэкапа.
Контрольные хеши можно вычислять потоково, с явным разделением SQL NULL и
строк и с длинами значений, чтобы исключить неоднозначную конкатенацию.

Сверь схему и историю Flyway с ожидаемой фазой после переименования. Убедись,
что runner выполняет UPDATE только raw_results и, отдельно при необходимости,
одной записи checksum V2. Для остальных таблиц не должно быть DML/DDL.
После commit закрой соединение, открой заново и повтори проверку совпадения
с expected и отсутствия необходимых UPDATE при том же исходном бэкапе.
Проверь чтение обоих raw-полей ListOfObjectsJsonAttributeConverter.

Репетиция должна включать принудительное прерывание между порциями и
возобновление; итог сравни с бэкапом так же, как при непрерывном выполнении.
Оцени длительность простоя, память и рост файла по фактическому объёму сервера.

8. Применение к оригиналу

Перед первым применением убедись, что приложение не запущено, оригинал всё ещё
совпадает с исходным бэкапом по SHA-256 и места достаточно по результатам
репетиции. Для возобновления уже начатого apply используй проверку из пункта 6.
Используй тот же проверенный runner с тем же хешем и настройками. Если оригинал
изменился до первого применения, выясни причину и повтори бэкап/репетицию для
актуального состояния.

Повтори проверенные шаги на явном оригинальном пути: dry-run, необходимая
фаза схемы, apply, dry-run с нулём изменений, verify против бэкапа, Flyway validate.
При сбое продолжай по правилам checkpoint либо восстанавливай бэкап; не
считай частично закоммиченные порции полным rollback всей операции.

Закрой все JDBC-соединения и запусти целевую версию приложения. Восстанови
прежнюю политику автозапуска. Проверь startup без ошибок Flyway/Hibernate,
health endpoint на фактическом серверном порту и просмотр исторической задачи
с raw_results в интерфейсе: структурированные ответы должны отображаться
объектами/массивами, скаляры и строки — соответствующими JSON-значениями.
Сохрани резервную копию и отчёты до завершения проверки эксплуатации.

9. Восстановление

При ошибке до commit откати текущую порцию. Если требуется полный откат,
останови приложение и все клиенты БД, сохрани неудачно мигрированный файл
отдельно и восстанови проверенную исходную копию в исходный путь с прежними
правами/владельцем. Убедись в совпадении SHA-256. Учти, что откатываются и
переименования/история Flyway: используй подходящую старую версию приложения
или повтори исправленную offline-миграцию до запуска новой версии.

10. Итоговый отчёт пользователю

Сообщи фактические пути БД, бэкапа, manifest/checkpoint и отчётов; версию runner
и целевого приложения; выполненные переименования; старый/новый checksum V2
или факт отсутствия необходимости его менять. Укажи количество проверенных
и изменённых задач, преобразований в объекты, массивы, числа, boolean, null
и строки, сохранённых исходных строк/null, длительность, пиковый расход
диска/памяти и результат независимой проверки.
Отдельно подтверди успешный повторный dry-run, Flyway validate и запуск сервиса.
